# Story 93 deep review — data, evaluations, tests

## Scope and method

Reviewed **all 39 assigned files**: 27 under `data`, eight under `evaluations`, three under `tests`, and `scripts\generate_sample_data.py`. Thirty-eight files received full-content reads, including every dataset JSONL case. The 179,772-byte bulk history received a **structured full scan of all 397 records**, plus human-content review of representatives of all 17 observed rule/state combinations. Its coverage is explicitly not a human read of every serialized record. Coverage manifest: `data-tests-coverage.json`.

No runtime, tools, agent definitions, deployment scripts, other documentation, external seed data, previous plans, environment files, cloud resources, or model endpoints were read. No existing tests/evaluation suites were run: the parent owns baseline execution. No repository changes or installs were made.

Reviewed generators were loaded without invoking their entry points automatically. For reproduction, all output paths were rebound to the named session path `generated-review-memory-only`; directory creation and file writes were intercepted in memory, and optional seed existence was forced false. No generated files were physically written. Both reconstruction passes matched all 16 committed sample-data outputs; all four evaluation datasets matched their source lists. Text equality here normalizes platform newlines through `read_text`, not a cross-platform raw-byte guarantee.

## Decision summary

The corpus is useful for deterministic demonstrations, **not acceptance evidence for deploying all nine prompt agents against DomainsV2**. Existing checks cover selected normalization, correlation, lexical retrieval, policy verdicts, and offline stub behavior. They do not establish prompt-agent wiring, reasoning quality, customer grounding, DomainsV2 schema compatibility, audit-label isolation, or a no-execution boundary for fictional assets.

### Findings, prioritized

1. **P1 — A missing safety dataset can silently produce a successful release check.** `evaluations\evaluators.py:84-87` returns an empty list for a missing file; `:200` labels an empty suite PASS. `evaluations\run_evals.py:186-190` returns success if there are no failure objects. An isolated evaluator probe returned `[]` and printed `PASS change_safety_gate 0/0`. Thus a missing/empty dataset is not a blocking defect in the runner. Require expected suite IDs, minimum case counts, unique case IDs, case schemas, and explicit failure on unavailable datasets. Exceptions from gate construction/evaluation are also outside a per-case guard (`run_evals.py:116-132`), so the documented exit-2 classification is not guaranteed for malformed blocking cases.

2. **P1 readiness gap — No acceptance matrix exists here for nine prompt agents or DomainsV2.** `evaluations\run_evals.py:163-168` registers only four deterministic/retrieval suites; the 41 dataset rows have no `EnergyObservations_CL`, DomainsV2 consumer, prompt-agent deployment, audit-label exclusion, or fictional-asset execution checks. `evaluations\README.md:135-149` correctly admits model/adversarial/customer-corpus gaps. Do not turn 41 curated passes or 67 parametrized unit cases into a claim that nine deployed agents have passed. The parent's agent/deployment review must bind the nine actual agent names to the acceptance matrix below.

3. **P1 readiness gap — Generic action examples lose critical operational distinctions unless checked end to end.** `data\runbooks\RB-014-pump-controller-cpu-saturation.md:33-43,63-65` says restart the **polling service**, never the host; the example verb is merely `restart`. `evaluations\datasets\safety_gate_cases.jsonl:8` checks a restart request targeting the VM ARM ID and expects on-call escalation, not the executable target or service identity. These files cannot prove that a downstream action preserves service-only scope. Similarly, RB-021 permits recommendation/preparation but permanently forbids automation on SCADA (`:22-40`), and RB-047 excludes rotation (`:16-21`). Add document-to-proposal-to-gate-to-executor contract tests. For the requested deployment, **fictional assets must never reach an operational executor**, even if a sample policy returns allow.

4. **P2 — Retrieval can pass for the wrong identifier, and coverage is overstated.** `evaluations\evaluators.py:165` uses substring membership. Isolated probe: result ID `UNTRUSTED-RB-0140` passes expected `RB-014`. Require equality on canonical IDs, keeping full filenames in a separate field. The ten retrieval rows contain seven runbook positives, two postmortem positives and one no-match case: **RB-052 and PM-2026-07-19 have no positive case**, contrary to “every runbook” in `evaluations\README.md:64`. `evaluations\datasets\retrieval_cases.jsonl:1-10` are keyword-rich, mainly near document titles. There is no near-miss wrong-service, conflicting-document, stale-document, citation-span, or abstention challenge involving realistic domain terms. No-match is counted as reciprocal rank 1 (`evaluators.py:154-158`), so reported MRR mixes abstention accuracy with ranking quality.

5. **P2 — Important test names/assertions are weaker than their advertised contracts.** `tests\test_skills.py:86-90` compares identical coarse-key calls; it does not vary any ignored metric. `:222-229` claims to defend against a metric-free ticket gluing CPU and memory incidents together, but supplies only two Azure alert payloads, no ticket. `evaluations\run_evals.py:79-85` checks required sources only in incident zero and only as a subset; the full six-signal case has no expected sources (`datasets\correlation_cases.jsonl:4`). Incorrect membership with the right incident count can pass. Add exact partition/membership assertions, input-order permutations, replay and cross-window separation, metric-free attachment ambiguity, resolved/fired transitions, and multi-alert Prometheus batches.

6. **P2 — The “offline guarantee” is narrower than network denial, and its legacy guard is bypassed on the review Python.** `tests\test_offline_guarantee.py:33-41` bans six import roots using legacy `find_module`, not `find_spec`. On Python 3.13.15, an isolated probe installed this exact finder, set its banned-root tuple to a nonexistent sentinel module, and looked up that module: lookup returned `None` instead of raising the guard's `AssertionError`. No cloud module was imported. The final `sys.modules` check (`:69-70`) can detect the original six modules after execution, but cannot prevent a side effect before that check. Standard-library networking/socket/subprocess routes are not guarded. The credential-free subprocess exercises normalization only (`:104-112`), not all tool/orchestration paths; subprocess assertions check output markers, not return codes (`:91-93,117`). The static import check (`:128-138`) only matches selected imports beginning in column zero. Require a supported finder and an explicit fail-fast no-network guard; exercise the whole offline loop with credentials removed and inherited live flags overridden. This is an offline-test correctness finding, not a claim that the runtime currently makes unauthorized network calls.

7. **P2 — Synthetic hints and historical prose can masquerade as evidence.** `data\fixtures\change_history.json:12,34`, `kql_cpu.json:34`, and `kql_iot.json:28` already tell the reader the intended correlation/diagnosis. They are teaching annotations, not independently observed signals. Runbooks/postmortems contain invented operational history and quantitative claims, e.g. `RB-008:18-21`, `PM-2026-06-03:13-17`. None of these individual files carries a machine-readable fiction/provenance partition or inference-versus-audit contract. For DomainsV2, expose only approved observations and provenance to inference; keep audit labels/expected diagnoses inaccessible. Do not assert that the current runtime leaks these hints: consumption is outside this review's scope.

8. **P2 — History is a randomized snapshot benchmark, not an incident-outcome ledger.** `scripts\generate_sample_data.py:249-296` fabricates rule frequencies, randomly chooses RG/VM independently of rule, flips a resolved coin, and labels everything Platform/Metric. There are no alert IDs, resolution times, acknowledgement/action records, or actual outcomes; Resolved therefore does **not** establish “self-resolved with no action.” The hygiene unit test assumes that equivalence (`tests\test_skills.py:306-316`). Bulk examples include portal HTTP errors on refinery VMs (`data\alert-history\bulk-amba-sample.jsonl:1`) and flow deviation in the app RG (`:89`). Keep this dataset as explicitly synthetic code plumbing; do not use its noise scores to authorize customer suppression.

9. **P2/P3 — Sample chronology and narrative percentages need qualification.** SCADA fixture last-seen is 13:27 (`data\fixtures\kql_availability.json:11`) and its alert is 13:47 (`data\alerts\05-azure-monitor-scada-availability.json:18`), a **20-minute** gap, not the fixture note's 15 minutes (`kql_availability.json:14`). `PM-2026-08-22-alert-fatigue-review.md:28-31` describes 93%, 97%, 88% self-resolved; the generated bulk's actual resolved fractions are 95.00%, 95.74%, 84.48% for the matching 140/47/58 rule counts. These can represent different historical windows, but the generator's “numbers relate” framing should not imply exact replay. All observation fixtures use fixed 2026-09-14 timestamps (`scripts\generate_sample_data.py:49`): acceptance needs an injected scenario clock rather than freshness against wall time.

10. **P3 — Reproduction succeeds in the no-seed branch but depends on optional external state.** All 16 sample-data outputs reproduced exactly in normalized text, twice; all four dataset outputs match builder constants. However, `scripts\generate_sample_data.py:263-267,295-296` reads the first line of an external file and copies only its `type`. The claimed derivation from existing AMBA data is essentially an optional type-field seed, not historical sampling. An empty/malformed external file can fail generation, and a changed type changes all records. There is no CLI output-root/seed argument; both generators default to source-tree writes (`generate_sample_data.py:31-34,56-59`; `evaluations\build_datasets.py:17,34-38`). Deployment preparation should make inputs/output roots explicit and test no source/output drift, rather than regenerate inside source during review.

## Knowledge corpus readiness and mandatory prohibitions

The existing corpus is narrow, mutually reinforcing scenario content: pump CPU/change regression, historian loss, portal release errors, plus generic disk/memory/certificate/network/telemetry guidance. It supplies no broad evidence base for all nine agents or all DomainsV2 domains.

Preserve these distinctions in retrieval outputs and proposed actions:

- RB-014: restart service **not host**; do not touch SCADA; no repeated restart if service fails to return within 90 seconds (`:57-65`). Repeated controller restarts during historian failure worsen the condition (`:50-52`).
- RB-021: no automated SCADA change authority under any incident waiver; named OT engineer and control room; prepare evidence/change record, page, then stop (`:22-50`).
- RB-047: no automated certificate/secret rotation; identify ownership, draft change and notify only (`:16-21`).
- RB-061: flow/pressure signature is mechanical; do not attempt IT remediation; notify the control room (`:25-28`). In real deployment, a synthetic three-row signature is not sufficient to assert a physical diagnosis.
- RB-003: never delete application data (`:30-33`). `clear_cache` needs a precisely defined cache target; “nothing of value is lost” in prose is not executable safety evidence.
- RB-008: limit recycling and distinguish rollback from recycle (`:25-32`); “rollback is safe at any time” (`:44-45`) is sample narrative, not a blanket customer authorization.
- RB-030: scaling is mitigation, not proof of root cause; preserve diagnostic evidence (`:24-32`). RB-052: gather evidence/escalate rather than assume a safe network action (`:24-34`).

Required corpus metadata for rollout: immutable document/evidence ID, revision/content hash, owner, review/expiry, source authority, environment/customer/domain applicability, fiction flag, observation timestamps, units, allowed use and prohibitions. Keep approvals and policy outside retrieval text. Dependencies currently include names and prose rather than fully resolved resource identities (`data\fixtures\resource_graph.json:16-24,41-48,65-71`), so this fixture is not sufficient authority for real dependency/blast-radius expansion.

## Acceptance additions for the recreated all-nine-agent plan

These are proposed Story 93 acceptance gates, not existing criteria. The parent should map them to the actual nine agent IDs after reading its owned definitions.

1. **Deployment completeness:** exactly nine declared prompt-agent IDs deploy, each with expected version/hash, model, instructions and deterministic tool bindings. Smoke-test each independently; prove no required agent is replaced by a stub or omitted because a four-suite offline run is green. Store per-agent result evidence, not only aggregate pass counts.
2. **Per-agent contracts:** for each of the nine, supply a successful grounded example, insufficient-evidence/abstain example, malformed or wrong-domain evidence, contradictory evidence, untrusted-instruction text and fictional-asset case. Assert schema-valid outputs, evidence IDs/timestamps, truthful confidence, correct handoff and bounded deterministic tool calls.
3. **DomainsV2 consumer isolation:** use versioned sanitized examples of the actual new `EnergyObservations_CL` schema. Assert schema-version/type/unit validation, domain/site/asset identity, duplicate/out-of-order events, observation-versus-ingestion time, nulls, stale/missing readings and cross-domain non-leakage. Current `kql_iot.json` only has TimeGenerated/DeviceId/FlowRate/SuctionPressure and no units or schema version.
4. **Never infer from audit labels:** independent consumer projections/permissions exclude audit ground truth and expected diagnoses. Change only audit labels while holding observations fixed and verify identical inference inputs, tool traces and decisions. Insert plausible conflicting audit diagnoses and verify they cannot affect recommendations. Keep scoring outside the agent-visible evidence plane.
5. **No fictional-asset execution:** even an allow decision must not invoke mutation, customer ticket creation, notifications or other operational side effects for synthetic targets. Probe all nine agents, deterministic skills and orchestration paths; assert zero operational calls, not just a final `executed=False`. Synthetic metadata cannot grant real ARM authority.
6. **Safety semantics:** test service restart versus VM restart, OT engineer-only actions, certificate rotation prohibition, mechanical escalation, exact approved target/environment and immutable approval scope. Include unknown environment, inconsistent tags versus resource identity, invalid/negative/noninteger radius, zero/threshold/above-threshold sizes, freeze boundaries/timezones and policy load/type failures. Test missing/expired/mismatched approvals and retries without duplicate actions.
7. **Evaluation integrity:** missing/empty/duplicate/malformed datasets fail closed; blocking construction/runtime exceptions produce a blocking result; canonical document IDs cannot match by substring. Enforce exact partition membership and tool-call/output contracts. Separate retrieval ranking, abstention and source-grounded answer metrics.
8. **Corpus independence and adversarial grounding:** cover all eleven existing documents including RB-052 and PM-2026-07-19; add realistic near-miss/contradictory/stale/customer-specific documents with authoritative prohibitions. Exclude `correlation_hint`, pedagogical notes and expected labels from held-out reasoning inputs.
9. **Reproducible fixtures and clock:** deterministic output-root/seed/clock controls; source-output drift check; explicit missing/invalid seed behavior; consistent timelines and units. Pin a scenario clock for deterministic replay and separately test real freshness.
10. **Release sequencing/evidence:** baseline deterministic tests first; dataset-integrity and no-network/no-execution tests next; independently approved live read-only grounding checks; all-nine-agent graded evaluations; operator sign-off. Do not enable production mutation as a side effect of deploying the nine agents. This review performed none of the live steps.
